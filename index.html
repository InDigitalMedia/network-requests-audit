The chain, and where the browser stops seeing it

Tracking travels through five stages. The Network tab in your browser can only see the first four. Everything a server container does after it receives a request is structurally invisible to DevTools — not hidden, not hard to find, genuinely not there. Most false passes in a server-side audit come from forgetting this.

Stage 1 · visible
Browser
The page loads and runs scripts. You see the script files arrive.
Stage 2 · visible
Tag manager
GTM decides which trackers are allowed to run, based on triggers and consent.
Stage 3 · visible
Tag fires
An individual tracker builds its payload — event name, value, user data.
Stage 4 · visible
Network request
The payload leaves the browser. This is the row you see in DevTools.
Stage 5 · invisible
Platform
With sGTM, your server forwards onward. Server-to-server. DevTools never sees it.
The one rule to remember
A 200 or 204 from your own tagging domain means your server accepted the request. Nothing more. Your container can accept a hit and then match no client, match the wrong client, fail a consent check, or get a 4xx back from Google — and the browser still shows a healthy green row. Only server container Preview, or the destination platform itself, proves delivery.

What do you want to check?

Pick the job below that matches your question. Each one is a short set of steps ending in a plain answer. You do not need to understand how any of it works, and you cannot break anything — everything here only reads what a page has already done.

First, install the one-click checker

Drag the black button on the right onto your browser's bookmarks bar. Then on any page, click it and you will get a list of the tracking that page has fired. This replaces every fiddly step involving developer tools — it is the single thing that makes the rest of this quick.

Two platforms need one extra click. TikTok and Snapchat hide their data inside the request rather than in its address, so the panel will name them but show no detail. Click Record payloads in the panel, repeat the action, then click the bookmark again. It only works for actions that stay on the same page.

Can't see your bookmarks bar? Press Cmd+Shift+B on a Mac, or Ctrl+Shift+B on Windows. If dragging does not work, use Copy the code instead, then create a new bookmark manually and paste it into the address or URL field.

On a phone or tablet? Bookmarklets are unreliable on mobile browsers — do this step on a desktop browser instead.

Drag the button to your bookmarks bar
1Is this page being tracked at all?2 minutes

The most common question, and the fastest to answer. Use this after a site change, a new landing page going live, or any time a report looks emptier than it should.

  1. Open the page in a new incognito or private window — Cmd+Shift+N on a Mac, Ctrl+Shift+N on Windows. This makes you look like a brand-new visitor.
  2. Accept the cookie banner if one appears. Tracking is often not allowed to run until you do, so skipping this produces a false alarm.
  3. Click the "Check tracking" bookmark. A panel appears listing what fired.

What good looks like: you see a heading saying a number of tracking events were found, with Google Analytics listed, plus whichever ad platforms you expect to be running.

If it says nothing found: turn off any ad blocker and reload — that is the cause most of the time. Then check you actually accepted the banner. If it is still empty after both, that is worth reporting.

2Did my form submission or enquiry get recorded?5 minutes

Use this before trusting lead numbers, and always after a form is changed or moved.

  1. In a new incognito window, go to the page with the form and accept the cookie banner.
  2. Actually complete and submit the form. Use an obviously fake name so the lead is easy to spot and discard — "Test Test" and a test email address.
  3. On the thank-you page that follows, click the bookmark.
  4. Click Copy all for the decoder, then open the Decode tab here and paste.

What good looks like: the decoder shows an event with a name that clearly describes a lead — something like generate_lead, form_submit or contact — and the verdict is green or amber.

If no event appears on the thank-you page: check whether the form redirects somewhere unexpected, or opens in a popup rather than loading a new page — both break tracking in ways that are easy to miss. Note down the exact URL of the thank-you page before reporting it; that is the first thing anyone will ask.

If the decoder flags personal data sent unhashed: stop and report that straight away rather than continuing. It means a real email address or phone number is being sent to an advertising platform in readable form, which is a data protection issue rather than a measurement one.

3Did a purchase or booking get counted?5 minutes

The highest-stakes check, because errors here change reported revenue and therefore what the ad platforms optimise towards.

  1. Complete a real test transaction in a new incognito window, accepting the cookie banner first. Use whatever test payment method your finance or development team has set up — do not use a real card without asking.
  2. On the order confirmation page, click the bookmark, then copy and paste into the Decode tab.

What good looks like: a purchase event, and — this is the part worth checking carefully — a value that matches the order total exactly, with the right currency. Compare it against the number on the confirmation page in front of you.

If the value is wrong: note whether it is out by delivery costs, by tax, or by a currency conversion. That distinction tells whoever fixes it roughly where the fault is, and saves a round of questions.

If you see two purchase events for one order: refresh the confirmation page and check again — some setups incorrectly count a refresh as a second sale, which inflates revenue. Worth reporting with the exact steps you took.

4Is our cookie banner actually working?6 minutes

This is a legal exposure, not just a measurement question, so it is worth doing properly. It needs two passes because you only get one consent decision per visitor.

  1. Pass one. New incognito window, load the page, accept all. Click the bookmark. You should see tracking events.
  2. Pass two. A brand-new incognito window — not the same one — load the page and reject all non-essential cookies. Click the bookmark again.
  3. Copy the result from pass two into the Decode tab.

What good looks like: after rejecting, either far fewer requests than pass one, or requests that the decoder reports as having advertising and analytics denied.

If pass two looks identical to pass one, or the decoder says permissions were granted by default, report it the same day and say which pass you were on. It means tracking is running before visitors agree, which is the wrong way round under UK and EU rules.

5A platform is reporting fewer conversions than our website10 minutes

Meta, Google Ads or LinkedIn showing fewer conversions than your own site data. Almost always one of four causes, and you can rule out three of them yourself.

  1. Check the obvious mismatches first. Are you comparing the same date range, the same time zone, and the same conversion definition? Platforms credit a conversion to the day of the click, not the day of the sale, so a like-for-like comparison is rarely as simple as it looks. This explains most gaps.
  2. Confirm the conversion fires at all using task 3 above. If it does not, that is your answer.
  3. Check the platform's own diagnostics. Meta Events Manager and Google Ads both have a status area that flags problems on their side, including duplicate or missing data — look there before assuming the website is at fault.
  4. Test with an ad blocker turned on. If the conversion vanishes, you have found the cause: a proportion of real visitors block tracking, so browser-based conversion counts are always somewhat lower than reality. This gap is normal and expected, not a bug.

Expect some gap regardless. A platform seeing fewer conversions than your website is the normal state of affairs, not a fault. It is worth investigating when the gap is large, or when it changes suddenly.

If you get through all four and it still does not add up: that is a genuine one to raise. Include the date range you compared, the two numbers, and what you ruled out.

What this can and cannot tell you
These checks show what your website sent. They cannot confirm what a platform did with it afterwards. So they are very good at catching "this is not being tracked" and "this is being tracked wrongly", and no use at all for "this arrived safely". If a check passes but the numbers still look wrong, the problem is further down the line and needs someone with access to the platform itself.

Start here — if you have never opened the Network tab

No prior knowledge assumed. By the end of this page you will be able to capture a tracking request from any website and have this tool tell you what it is and whether anything is wrong with it. It takes about ten minutes the first time and under a minute after that.

The one idea everything rests on
When you open a web page, it quietly sends out dozens of small messages to other companies. Most carry tracking: "someone viewed this product", "someone bought something, here is the order value". Each message is a network request. They are invisible unless you deliberately look — and looking at them is the only way to know whether tracking actually works, because a dashboard showing no sales looks identical whether sales stopped or the tracking broke.

Your first five minutes

If you only do four things, do these.

  1. Open the page you want to check in a new incognito or private window. In Chrome that is File → New Incognito Window, or Cmd+Shift+N on a Mac, Ctrl+Shift+N on Windows. This matters because a normal window remembers you — old cookies, a consent choice you made months ago — and you want to see what a brand-new visitor sees.
  2. Open the developer tools before you load the page. Press F12, or Cmd+Option+I on a Mac, or Ctrl+Shift+I on Windows. A panel opens, usually at the bottom or the side. Click the tab labelled Network. On Safari you have to switch this on first: Safari → Settings → Advanced, then tick the option about showing web developer features.
  3. Now reload the page. The Network panel fills with rows. This ordering is the single most common mistake — the panel only records what happens while it is open, so if you open it after the page has loaded you will see almost nothing and conclude the tracking is broken when it is fine.
  4. Type collect into the filter box at the top left of the Network panel. Most analytics requests contain that word. If nothing appears, do not panic — see "when the filter finds nothing" below.

Reading the rows

Each row is one message sent out by the page. Six columns matter.

Name
The end of the address — usually the path, like /g/collect. Often shortened, so it can look like gibberish.
Status
Whether it arrived. Green or a number in the 200s is normally fine. Red is a failure. But see the warning below — healthy is not always 200.
Domain
Who received it. The most useful column. Turn it on by right-clicking any column heading and ticking Domain.
Type
What kind of message: a script download, an image, a data call.
Size
How much data came back. Tracking replies are usually tiny or empty, which is normal.
Initiator
What caused this request. Useful for tracing which script fired a tag.
Do not assume red is bad and green is good
Several tracking services deliberately reply with something other than 200. Google Analytics returns 204, LinkedIn returns 302, Microsoft returns 204, and Floodlight returns 302 and then 200. None of those is a fault. Equally, a healthy green 200 from a server container proves only that the message was received — not that it was passed on to Google. Check the Platforms tab for what each service should return before you raise anything.

Getting a request into this tool

  1. Find the row you care about. If you are checking a purchase, do the purchase with the panel open and watch for new rows appearing. Anything containing collect, /tr or /adsct is likely to be tracking.
  2. Right-click the row. Choose Copy, then Copy as cURL. That sounds technical but it is just "copy everything about this message". If you only see Copy link address, that works too — it gets the address but not the contents.
  3. Go to the Decode tab in this document and paste it into the box. It decodes as soon as you paste. Nothing is uploaded anywhere — it all happens inside this file on your own machine, which matters because these requests can contain real visitor data.
  4. If you know your organisation's tagging domain — something like metrics.yourcompany.com — put it in the small box next to the Decode button. The tool can then tell you whether each request went through your own server or straight out to Google, Meta and the rest.
  5. Read the findings first, then the parameters. Findings are the verdict; parameters are the raw detail behind it.

What the verdicts mean

✓ PASS
Working as it should. Nothing to do.
▲ WARNING
Not broken, but worth a look. Often a design choice with a downside you should be aware of.
✕ FAIL
Something is wrong and it has a real consequence — wrong numbers, missing data, or a compliance problem.
· NOTE
Context, not a judgement. What the event was, how many custom fields it carried, and so on.

Each verdict explains the business impact, not just the technical fault — because "the event ID is missing" means nothing on its own, whereas "your conversions will be counted twice, so your return on ad spend looks better than it is" is something you can act on and explain to someone else.

When the filter finds nothing

This is common and usually not a fault. Work through it in this order.

  1. Did you open the panel before loading the page? If not, reload with it open. This fixes it most of the time.
  2. Clear the filter box entirely and look at how many rows there are. If there are plenty, the filter word was simply wrong for this site.
  3. Try filtering by the company instead of the path — type google, or facebook, or your own company name.
  4. Try tid= instead. Every Google Analytics message carries this, whatever its address. Many organisations deliberately scramble the addresses of their tracking requests so ad blockers cannot recognise them, which makes filtering by path useless — this is the single most confusing thing for a newcomer, and it is intentional rather than broken.
  5. Turn off your ad blocker and reload. Ad blockers stop tracking requests from being sent at all, so you will see nothing and wrongly conclude the tags are missing.
  6. Check whether you accepted the cookie banner. On a site that follows the law properly, tracking should not fire until you agree — so no requests may be the correct behaviour, not a bug.

Testing consent properly

This is where most real problems hide, and it needs two passes. Both in a fresh incognito window, because you only get one consent decision per visitor.

  1. Pass one — accept everything. Load the page, accept all cookies, then check that analytics and advertising requests appear. If they do not, tracking is broken.
  2. Pass two — reject everything. Open a new incognito window, load the page, reject all non-essential cookies. Now the analytics and advertising requests should either stop or continue in a stripped-down cookieless form. If they carry on exactly as before, that is a compliance problem, not a technical curiosity — and worth escalating the same day.
  3. Paste a request from each pass into the Decode tab. It reads the hidden consent parameters and tells you in plain English what permissions were recorded. That is far more reliable than watching which tags appear to fire.

Jargon, in plain English

Tag
A small piece of tracking code that does one job, such as recording a purchase.
Tag manager / GTM
Google Tag Manager. A control panel that lets people add or change tracking without editing the website itself.
Trigger
The condition that makes a tag fire, such as "when someone reaches the thank-you page".
Pixel
A platform's own tracker that runs in the visitor's browser — the Meta Pixel, the LinkedIn Insight Tag.
Hit / event
One recorded action. A page view, a click, a purchase. Each becomes one network request.
dataLayer
A hidden list of information the page keeps for tracking purposes, which tags read from.
GA4
Google Analytics 4, Google's current website analytics product.
Measurement ID
Identifies which analytics property data belongs to. Looks like G-ABC123XYZ.
Server-side / sGTM
Running the tag manager on a server you control instead of in the visitor's browser, so tracking is harder to block.
Server container
That server. Requests go to your own web address first, and it decides what to forward onward.
Tagging domain
The web address of your server container, usually a subdomain of your own site.
Conversions API / CAPI
Sending the same tracking from a server rather than a browser. More reliable, but risks double-counting.
Deduplication
Telling a platform that a browser event and a server event are the same action, so it counts them once.
Event ID
The shared reference that makes deduplication work. Missing it is a common and expensive fault.
Consent mode
The system that tells Google's tags whether the visitor agreed to be tracked.
CMP
Consent Management Platform — the tool that shows the cookie banner and records the answer. OneTrust, Cookiebot, CookieYes.
Hashed
Scrambled into an irreversible code for privacy. Must be done a specific way or the platform cannot use it.
Parameter
One piece of information attached to a request, written as name=value.
First-party / third-party
First-party means it comes from the site you are on. Third-party means another company's domain, which browsers increasingly block.
4xx / 5xx
Status numbers meaning the request failed. Think of them as a "delivery failed" notice.

The limit of all of this
The browser shows you what left the page. It cannot show you what a platform did with it, and with a server-side setup it cannot show you anything the server did after receiving the message. So the browser is excellent for "did this go to the right place, carrying the right information" and useless for "did it arrive". For arrival you need the server container's own Preview mode, or the platform's own reporting — Google Analytics DebugView, Meta Events Manager. Anyone who tells you a green row proves the tracking works has stopped looking one step too early.

How to identify any request in four looks

Before the tables — the method. Every tracking request answers to the same four questions, and you can usually name it from the first two.

  1. Hostname (the Domain column). Who is receiving this? google-analytics.com is analytics; facebook.com is Meta; your own subdomain means it has been routed through a server container. The hostname is the one thing that cannot be disguised.
  2. Path. What kind of request is it? /g/collect is a GA4 event; /gtag/js is a library download; /tr is a Meta event. Note that server containers frequently randomise paths to evade ad blockers, so a meaningless path is not automatically a fault.
  3. Parameters. What is actually being sent? For GET requests these are in the URL. For POST requests — Meta, TikTok, Snapchat — the URL tells you almost nothing and you must open the Payload tab.
  4. Status and size. Did it land? Be careful: healthy is not always 200. GA4 returns 204, LinkedIn returns 302, Floodlight returns 302 then 200. A red row is a problem; a non-200 row often is not.

ord= does two completely different jobs depending on how the tag counts, and getting it the wrong way round is a common, quiet misconfiguration. Server-side GTM endpoints

A server container is a copy of Tag Manager running on a server you control, on your own subdomain, instead of in the visitor's browser. The browser sends one request to it; the container decides what to forward onward. A client is the component inside the container that claims an incoming request and translates it into an event — and the first client that matches wins, which is itself a source of bugs.

Debugging a server-side setup — what you can see and how

The question that comes up first: do you need to know the container's hostname in advance? No — not if you capture with the bookmarklet. It works out which requests belong to your own site by comparing each request's hostname against the site you are on, so a first-party container is identified without being told. That covers the common case, where the container sits on a subdomain of the main site.

Two situations where you do need the hostname:

  • The container is on an unrelated domain. If the tagging endpoint is not a subdomain of the site — a separate domain bought for the purpose, or a vendor-hosted endpoint — nothing in the request tells you it is yours. The bookmarklet will label it "Possible tracking" and you have to supply the hostname yourself. That is what the tagging-domain field on the Decode tab exists for.
  • You are pasting a URL by hand rather than capturing it, so there is no site context to work from.

Three ways to find the container hostname

  1. The bookmarklet. Anything grouped under "Your own domain (server-side)" is it. Quickest, and needs nothing but the page open.
  2. The Network tab's Domain column. Look for a hostname on your own domain receiving requests that carry tracking parameters. You may need to switch the Domain column on — right-click any column heading and tick it.
  3. The container configuration itself. In Tag Manager, the server container's settings list its tagging URLs. This is the authoritative answer, and worth cross-checking against what the browser actually does — they diverge more often than you would expect, usually after a migration.

The two legs, and what proves each

A server-side setup has two hops, and they need completely different tools. Conflating them is the single most common mistake in a server-side audit.

LegVisible inWhat proves it workedWhat does not
Browser → your container The Network tab, or the bookmarklet. A request to your tagging domain with a response in the 200s or a 204, carrying the parameters you expect. Nothing about the platform. This leg passing tells you the handover happened, and that is all.
Your container → the platform Nothing in the browser. Server-to-server, so DevTools never sees it. Server container Preview, which shows the incoming request, which client claimed it, which tags fired, and the response code each destination returned. A healthy response from your own container. It returns 200 whether it forwarded the data or silently dropped it.

A practical order of attack

  1. Confirm the request leaves the browser and goes to your domain rather than direct to a vendor. Bookmarklet, then Decode. If this fails, stop here — nothing downstream matters.
  2. Read the parameters. Right event name, right value, right consent state. A request that arrives with the wrong contents is worse than one that does not arrive, because it looks fine in every dashboard.
  3. Open server container Preview and repeat the action. Check a client claims the request — if none does, the container received it and threw it away. Then check the outgoing response codes.
  4. Check the destination platform. GA4 DebugView or Realtime, Meta Events Manager, the equivalent elsewhere. This is the only place that confirms arrival.
  5. If Preview looks right but the platform shows nothing, the problem is credentials or configuration on the outbound tag — an expired access token is the usual culprit, and it fails silently.
Two container-side traps worth knowing
Client priority. The first client whose path pattern matches an incoming request claims it, and no other client gets a look. A broadly-scoped client — the legacy Universal Analytics one is the usual offender — can swallow requests intended for another, producing the baffling symptom of a request arriving healthily while the tag that should handle it never fires. Check the claiming client in Preview before assuming the tag is broken.

Liveness versus correctness. A container has a health endpoint at /healthy — worth putting into uptime monitoring, because a container that is simply down is otherwise invisible until someone notices the reports have flatlined. It confirms the container is running, and nothing at all about whether it is configured correctly.
When the payload is encrypted
Some setups encrypt the request payload as well as randomising the path. Decryption happens before the request reaches the container, so the browser shows you nothing readable and this decoder cannot help. Server container Preview becomes the only view of what was actually sent — plan on that rather than fighting the browser.

When the paths are randomised

Server containers are frequently configured with meaningless paths and script filenames so ad blockers cannot pattern-match them. Some setups go further and encrypt the payload entirely. This is legitimate but it makes debugging genuinely harder, so work in this order:

  1. Filter by your container's hostname, not by path. The hostname is the one element that cannot be randomised.
  2. Search the Network tab for the measurement ID — G-XXXXXXX. Reliable on plain payloads; fails once payloads are encoded.
  3. Open the request body, not just the URL. Encoded and POSTed payloads move all the useful detail out of the query string.
  4. Decode base64 payloads if present. Note the parameter name may itself be randomised, so do not hunt for a fixed key.
  5. Fall back to server container Preview, which shows the decoded incoming request. With encryption enabled this is the only readable view — decryption happens before the request reaches the container.
Worth saying to clients
Randomised paths carry a real maintenance cost, as this exercise showed — an undocumented path is invisible to the next person to debug the container, including a future you. If a client asks for ad-blocker evasion, transparency is a reasonable counter-position to put to them alongside the technical option. Weigh it deliberately rather than switching it on by default.

Do not try to read the gtm= parameter

Every GA4 hit carries something like gtm=45he68c1h1v88…. It is undocumented by Google, and the one public attempt to parse it concedes it is "not reverse-engineered yet". That attempt is also a client-side-rendered page, so it returns an empty shell to any script checking your citations — treat this as having no citable source. Do not use it to determine container version in an audit — read the version from GTM Preview or the container's Versions screen instead.

Consent signals on Google requests

Consent mode is the system that tells Google's tags whether the visitor has agreed to be tracked. Rather than simply blocking tags, it attaches the visitor's choices to each request as parameters. Reading those parameters is the fastest honest check of whether a cookie banner is actually wired up — far quicker than watching tags fire.

Sourcing split, because it matters if a client challenges you: Google officially confirms that gcs and gcd exist and what they are for — developers.google.com, consent mode concepts ↗ — but publishes none of the encoding below. Every value decode on this tab comes from Simo Ahava's consent mode v2 write-up ↗, which is reliable practitioner reverse-engineering, not documentation.

The gcs parameter — current state

Format G1xy, where x is advertising permission and y is analytics permission. 1 means granted, 0 means denied.

G100
Nothing granted. Ads denied, analytics denied.
G110
Ads granted, analytics denied.
G101
Analytics granted, ads denied.
G111
Both granted.

Two things this tells you. G100 only appears in advanced consent mode, where tags fire in a cookieless form before consent — in basic consent mode Google tags do not load at all until the visitor interacts with the banner, so you never see a denied hit. And inside a server container the same signal is exposed as x-ga-gcs — an internal event-data parameter on the incoming request, not an HTTP header (a common mislabelling). Google lists it but documents no semantics beyond a warning not to alter it.● Confirmed ↗

The gcd parameter — default versus update

Richer and more useful than gcs for auditing, because it distinguishes the default state from the state after the visitor chose. That is what proves consent mode was initialised correctly rather than bolted on late. Format is 11<ad_storage>1<analytics_storage>1<ad_user_data>1<ad_personalization>5, where each 1 is a separator and each slot carries a letter:

l
Not set via consent mode at all
p
Denied by default, no update
q
Denied by default and after update
t
Granted by default, no update
r
Denied by default, granted after update
m
Denied after update, no default
n
Granted after update, no default
u
Granted by default, denied after update
v
Granted by default and after update

gcd appears on all hits to Google services, even when consent mode is not active. A slot reading l where you expected r is the signature of a CMP that is not actually talking to Google's tags.● Confirmed ↗

What a compliance red flag looks like
For a European visitor who has not yet chosen, gcd slots reading t or v — granted by default — means advertising and analytics permissions were switched on before the visitor agreed. Under GDPR that is the wrong default, and it is a finding worth raising immediately rather than filing as an observation.

Related parameters — treat with caution

  • dma — commonly read as a flag that EEA/Digital Markets Act consent rules apply to the hit. Could not be verified.○ Unverified
  • dma_cps — understood to list which Google services consent covers, as a letter string such as syphamo. No reliable letter-to-service mapping exists; do not publish one.○ Unverified
  • npa — npa=1 is understood to mean non-personalised ads. Single secondary source only.○ Unverified
  • Trailing digit on gcd (usually 5) — one source describes it as ads-signals status. Not confirmed.○ Unverified
  • em on Google Ads traffic — this one is confirmed and it is the single most useful check for enhanced conversions. A real SHA-256 hash means it is working. em missing entirely means the tag is misconfigured; tv.1~em. means empty data was passed; tv.1~em.e1 means there is a problem with the data you are sending — not a transmission failure. Different diagnosis, different fix.● Confirmed ↗

Record your own setup

Server-side containers are usually configured with randomised hostnames, paths and script filenames so ad blockers cannot pattern-match them. That is a legitimate choice, but it means none of it is guessable by the next person to debug the site — including a future you. Fill this in once per site and keep it somewhere findable.

Fill this in from a live capture, not from memory
Load the site, click the Check tracking bookmark, and read the values off the panel it produces. Anything you write down from memory or from a config screen may not reflect what the site actually does today.

Status checklist — work through this per site

  • Is analytics routed rather than duplicated? Exactly one analytics request per event, going to your own domain, with nothing going to google-analytics.com. Two means the redirect is half-applied and you are double-counting.
  • Are the scripts first-party too? Setting a server container URL reroutes the measurement but not the tag library. Both coming from your domain means the full setup, not just half of it.
  • Has anything actually arrived? A healthy response from your own container proves only that your server received the request. Confirm in the destination platform — this is the check people skip.
  • What is the consent state? Decode a request and read the consent parameters. For a UK or EU-facing site this is the highest-priority item, and it is a compliance question rather than a technical one.
  • What still bypasses the container? Usually Google Ads, Floodlight, or any platform nobody got round to migrating.
  • Safari cookie lifespan. Check how the tagging hostname resolves, per the note below.
Safari, CNAME cloaking and the 7-day cap
WebKit's documented behaviour: Safari "detects third-party CNAME cloaking requests and caps the expiry of any cookies set in the HTTP response to 7 days", triggered by a first-party subresource resolving through a CNAME that differs from the first-party domain — WebKit, CNAME cloaking and bounce tracking defense ↗. Business impact, plainly: a CNAME-based server-side setup does not buy long-lived visitor cookies in Safari. Returning visitors are counted as new after 7 days, attribution windows silently truncate, and new-versus-returning reporting degrades. The documented mitigation is a same-origin or A-record deployment rather than a CNAME.

Keep this distinct from Safari's other 7-day rule — script-writable storage is deleted after 7 days without first-party interaction, regardless of CNAME (WebKit ↗). Conflating the two is a common error.

Currency caveat. That 2020 post says the cap is "aligned with ITP's expiry cap on all cookies created through JavaScript" — that clause is now stale, as WebKit later removed the expiry cap on JavaScript cookies. The CNAME cap on HTTP-response cookies and the 7-day storage deletion both still apply, and WebKit has since extended the cap to responses from third-party IP addresses too. Do not present the 2020 post as a description of current behaviour without this note.

Which requests actually tell you something

Not every row is worth your attention. Ranked by how much diagnostic value each one carries when you are debugging a server-side setup.

Worth investigating

  • The event hit to your container. Presence, path, status, and above all the parameters. This is where the data is.
  • gcs and gcd. The fastest read on whether the cookie banner is genuinely wired up.
  • Anything still going direct to a platform. Tells you what has not been migrated, and what remains blockable.
  • /set_cookie requests. Their presence means some tags are forcing browser-side pixels — so they are not truly server-side.
  • Genuine 4xx and 5xx. A real delivery failure.
  • Duplicate hits with the same event name. The classic double-counting signature.

Usually noise

  • Library downloads (.js files). Confirm they load, then move on — unless you are auditing whether they are first-party.
  • Cookie-matching and sync pings. LinkedIn's 302, Snapchat's /cm/ paths. Normal, and not where bugs live.
  • Missing doubleclick.net hits. Almost always the tester's own ad blocker or browser protection, not the implementation.
  • Non-200 statuses on known endpoints. 204, 302 and even 400 are the healthy state for several platforms — check the table before raising it.
  • Undocumented Google endpoints — /a?, ga-audiences, 1p-user-list. Real, but nothing can be concluded from them.

A specific, high-frequency bug worth knowing

In the web container's debug view, a row labelled "gtag hit" means the event routed to your server container. A row labelled "Google Analytics Hit" means it went direct to Google, bypassing your server entirely. The documented root cause is the Google tag not being triggered before the GA4 event tags — so the first few events of a page load leak straight to Google while later ones route correctly. It produces a setup that looks fine in spot checks and quietly splits your data. Source: Adswerve, troubleshooting sGTM GA4 hit routing ↗

Proving delivery, in order of authority

  1. Server container Preview. The only place you see both legs — the incoming request, which client claimed it, which tags fired, and the outgoing response codes from Google, Meta and the rest. Everything else is inference.
  2. The destination platform. GA4 DebugView or Realtime; Google Ads conversion diagnostics; Meta Events Manager including event match quality and the dedup view; the equivalent for TikTok, LinkedIn and Snap.
  3. Server and hosting logs. Cloud Run, App Engine or Stape request logs.
  4. The browser. Useful for routing — did the hit go to the right host — and for reading parameters. Useless for delivery. Do not let a green row end the investigation.

Standing checklist for any URL

  • Test in an incognito window with cookies cleared, so you see what a brand-new visitor sees.
  • Is the tag manager script present and returning 200?
  • Is the dataLayer — the hidden list of information the page keeps for tracking — initialised before the container loads?
  • Are consent signals visible on outgoing requests, and do they match what the banner says?
  • Do tags fire on page load, and again on the actions that matter?
  • Any genuine 4xx or 5xx on a tag endpoint?
  • Reject all, then repeat: do the non-essential tags actually stay off?

Decode a request

Paste a request from the Network tab and this will name it, translate every parameter into plain English, and raise findings. Works with a full URL, a Copy as cURL paste, a bare query string, a POST body, or several lines at once. In DevTools: right-click the request → Copy → Copy as cURL, which includes the request body. Most platforms put the event name and every parameter in the address, so a plain URL is enough; TikTok and Snapchat put theirs in the body, so those need cURL or the bookmarklet's record mode.

Nothing leaves your browser
All parsing happens locally in this page — there is no server, no network call and no logging. That matters because real requests contain visitor data, and pasting them into an online decoder would itself be a data protection problem.

Evidence standard, and what not to state as fact

Rows are marked ● Confirmed against official documentation or the live library source, ◆ Live-tested where a real request was sent and the response recorded, and ○ Unverified where a claim is widely repeated but has no primary source. The distinction is the point of the document — an audit finding built on an unverified parameter meaning is a guess wearing a suit.

Three widely-repeated claims failed verification and were corrected here: TikTok's endpoint is /api/v2/pixel and /api/v2/pixel/track does not exist; Reddit's config host is pixel-config.reddit.com, not conversions-config.reddit.com; and Meta's external_id is sent as ud[external_id], not as a top-level parameter. Each would cause a real audit to look in the wrong place and report nothing found. The sGTM health endpoint is /healthy, not /healthz.

A second verification pass in August 2026 corrected four claims that appeared in an earlier draft of this document: the tag gateway does not forbid /gtm as a reserved path — Google suggests it — and does not always need two paths; em=tv.1~em.e1 signals a data problem, not a transmission failure; x-ga-gcs is an internal event-data parameter, not an HTTP header; and the sGTM GA4 client claims /collect and /j/collect as well as /g/collect. The same pass found that /g/collect returns 204 in practice while Google's own page says 200, and that region1.analytics.google.com — the host EU browser hits actually use — is undocumented.

Known gaps where no citable source exists at all: the en parameter, any surviving Universal Analytics parameter spec, the Measurement Protocol client's default path in sGTM, which domain serves sw_iframe.html per product, and any decoder for gtm=. Four Google URLs that used to cover this ground are now dead or redirecting, and have been deliberately left uncited.

Do not publish as fact: the role of ccm/collect or its parameters; the purpose of gtag/destination, googletagmanager.com/a?, 1p-user-list or ads/ga-audiences; any decoding of gtm=; the dma_cps letter mapping; or GA4 region hosts above region1.
